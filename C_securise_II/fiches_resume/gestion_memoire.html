📦 Gestion Dynamique de la Mémoire en C

La gestion dynamique permet d'allouer de la mémoire sur le Tas (Heap) à l'exécution. Elle offre une flexibilité indispensable pour les structures de données dynamiques, mais requiert une rigueur absolue pour éviter les failles critiques.

🎯 Pourquoi Recourir à l'Allocation Dynamique ?

En C, les tableaux locaux déclarés sur la pile nécessitent une taille fixée ou limitée à la durée d'exécution du cadre de la fonction (stack frame). Dès que la fonction se termine, sa pile est invalidée.

L'allocation dynamique répond à trois impératifs majeurs :

  • Taille inconnue à la compilation : Charger un fichier dont le volume varie, lire des paquets réseau ou accueillir une saisie dynamique.
  • Persistance des données : Créer une structure (ex: nœud de liste chaînée) dans une fonction et pouvoir la transmettre à d'autres modules sans la détruire au return.
  • Volumes de données importants : La pile (Stack) étant restreinte (quelques Mo), stocker de gros buffers en mémoire vive impose de passer par le Tas (Heap).

🔄 Le Cycle de Vie d'un Bloc Dynamique en 4 Temps

1
Calcul de Taille

Multiplication du nombre d'éléments par sizeof(type).

2
Allocation & Contrôle

Appel de malloc/calloc et vérification impérative contre NULL.

3
Exploitation

Lecture et écriture en respectant scrupuleusement les bornes.

4
Libération & NULL

Appel de free() suivi immédiatement de ptr = NULL.

cycle_de_vie_heap.c 
#include <stdio.h>
#include <stdlib.h>

int traiter_scores(size_t nb_joueurs) {
    // ÉTAPE 1 & 2 : Allocation et test immédiat
    int *scores = (int *) malloc(nb_joueurs * sizeof(int));
    if (scores == NULL) {
        perror("Allocation impossible (mémoire épuisée)");
        return -1;
    }

    // ÉTAPE 3 : Exploitation sécurisée
    for (size_t i = 0; i < nb_joueurs; ++i) {
        scores[i] = (int)(i * 100);
    }

    // ÉTAPE 4 : Libération et désarmement
    free(scores);
    scores = NULL; // Bannit le pointeur suspendu

    return 0;
}

⚠️ Les 4 Dangers Mortels de la Mémoire Dynamique

La liberté accordée par le C s'accompagne d'un risque élevé de vulnérabilités répertoriées au Common Weakness Enumeration (CWE) :

🚰 Fuite de Mémoire (Memory Leak - CWE-401)

Oublier de libérer un bloc ou écraser l'unique pointeur le référençant. La mémoire consommée n'est jamais rendue à l'OS avant l'arrêt du processus.

💥 Déréférencement NULL (CWE-476)

Utiliser directement l'adresse renvoyée par malloc sans tester si elle vaut NULL (cas d'échec d'allocation). Provoque un crash immédiat.

👻 Pointeur Suspendu & Use-After-Free (CWE-416)

Continuer à lire ou écrire à travers un pointeur après avoir exécuté free(ptr);. Permet à un attaquant de corrompre des données nouvellement réallouées.

💣 Double Libération (Double Free - CWE-415)

Appeler deux fois free() sur le même pointeur sans réallocation intermédiaire. Corrompt les structures internes de l'allocateur (ptmalloc).

🛡️ L'astuce défensive : pourquoi free(NULL) est inoffensif
Le standard C stipule que si le paramètre passé à free() est un pointeur NULL, la fonction ne fait strictement rien et ne génère aucune erreur. Dès lors, assigner ptr = NULL; après libération protège contre les crashs en cas de second appel accidentel à free(ptr); !

💡 Bonnes Pratiques Architecturales

  • Principe de responsabilité (Ownership) : Identifiez clairement quelle entité est responsable de la création et de la libération d'une ressource.
  • Couples d'initialisation / destruction : Pour vos structures personnalisées, créez systématiquement des fonctions appariées : mon_type_create(...) et mon_type_destroy(mon_type_t **ptr).
  • Audit dynamique continu : En séance de TP, compilez toujours avec les drapeaux de détection mémoire : gcc -Wall -Wextra -g -fsanitize=address,undefined.
